# Canopée Database Schema

Business rules, conventions, and open questions for the Canopée database.

**Sources of truth:**

- Column structure, types, and constraints → [`schema.dbml`](../schema.dbml)
- Business rules and conventions → this file
- SQL constraints not expressible in DBML → migrations (once Sprint 1 begins)

Visual: [dbdiagram.io view](https://dbdiagram.io/d/database-schemas-6a692a67067336e1de14d56f)

## Stack

- **Database:** PostgreSQL (via Supabase)
- **Auth:** Supabase Auth handles passwords, sessions, and password resets. Auth users live in the `auth` schema; application user profiles live in `public`.
- **Schema design:** DBML in [dbdiagram.io](https://dbdiagram.io/)

## Conventions

Apply to every table unless a specific table's doc calls out an exception.

- **IDs** are `uuid`, generated by the database.
- **Timestamps** are `timestamptz`.
- **`created_at`** on every table, defaulting to `now()`. Add `updated_at` when a row is mutable.
- **Enum values** are lowercase snake_case.
- **Foreign keys** are named `<table_singular>_id` (e.g. `user_id`, `patrol_id`).
- **Coordinates** use `decimal(9,6)` (≈11cm precision, standard for GPS).
- **Citizens are not users.** Public reporters interact with the app without accounts; their email is captured on the report itself.

### Where logic lives

- **Structural integrity** (types, NOT NULL, UNIQUE, FK, PK) → database
- **Business rules** (workflow, defaults, product decisions) → application code
- **Security-critical rules** (auth, permissions, data access) → both database (Supabase RLS) and application code

## Enums

### `user_role`

Permission level. Assigned at signup (defaults to `volunteer`) or manually by an admin.

| Value       | Meaning                                              |
| ----------- | ---------------------------------------------------- |
| `volunteer` | Default role for public signups                      |
| `pro`       | Professional user, assigned manually by an admin     |
| `admin`     | Full permissions, assigned manually by another admin |

### `user_status`

Approval state for the account.

| Value      | Meaning                                            |
| ---------- | -------------------------------------------------- |
| `pending`  | Awaiting admin review (default for public signups) |
| `approved` | Active account                                     |
| `rejected` | Denied by an admin                                 |

### `report_category`

Type of report. Tentative list from PRD — **pending Canopée confirmation before Sprint 1**.

| Value                    | Meaning                                                        |
| ------------------------ | -------------------------------------------------------------- |
| `dangerous_tree`         | Dangerous trees or branches (fall risk, dead wood, etc.)       |
| `damaged_infrastructure` | Damaged benches, signs, fences, paths, etc.                    |
| `fauna_observation`      | Wildlife sighting. Only visible on the map to pros and admins. |
| `flora_observation`      | Plant sighting. Only visible on the map to pros and admins.    |
| `unleashed_dog`          | Off-leash dog observed on the site.                            |

## Tables

### `users`

Application user profile. One row per non-citizen user. Linked one-to-one with a Supabase Auth user via `auth_user_id`.

**Column descriptions**

| Column         | Description                                                        |
| -------------- | ------------------------------------------------------------------ |
| `id`           | Internal user id                                                   |
| `auth_user_id` | Links this profile to the Supabase Auth user. Cascade delete.      |
| `email`        | Contact email. Duplicated from `auth.users.email` for convenience. |
| `first_name`   | Given name. Nullable — see business rules.                         |
| `last_name`    | Family name. Nullable — see business rules.                        |
| `role`         | Permission level. See `user_role` enum.                            |
| `status`       | Approval state. See `user_status` enum.                            |
| `created_at`   | Row creation time                                                  |

**Business rules**

- `first_name` and `last_name` are nullable at the database level. Rows created
  before the columns existed have neither, and `ensureUserProfile` — the login
  fallback that creates a missing profile from the Supabase Auth user — only has
  an id and an email to work with. Requiring a name would break both. Collecting
  names at signup, and whether they are mandatory there, is a separate decision.
- Public signups create `role = 'volunteer'`, `status = 'pending'`.
- Pros and admins are created manually by an existing admin. They are never created through the public signup form.
- Admins are always `approved`. Enforced at the application layer per the convention above.
- Passwords are not stored here — Supabase Auth handles password hashing and validation.
- Permissions derive entirely from `role`. There are no per-user permission flags.

**FK to `auth.users` (SQL migration)**

Not visualized in dbdiagram because it targets a schema (`auth`) that dbdiagram doesn't know about.

```sql
alter table public.users
  add constraint users_auth_user_id_fkey
  foreign key (auth_user_id) references auth.users(id) on delete cascade;
```

### `reports`

Issue or observation submitted by either a user or a citizen (no account).

**Column descriptions**

| Column                   | Description                                                                     |
| ------------------------ | ------------------------------------------------------------------------------- |
| `id`                     | Internal report id                                                              |
| `event_number`           | Human-readable auto-incremented number. Used in URLs and support conversations. |
| `user_id`                | Set if the reporter has an account.                                             |
| `reporter_email`         | Set if the reporter is a citizen without an account.                            |
| `category`               | Report type. See `report_category` enum.                                        |
| `description`            | Free-text description of the report.                                            |
| `photo_url`              | Photo attached to the report. Required for fauna/flora categories.              |
| `latitude` / `longitude` | Location of the observation.                                                    |
| `resolved_at`            | `null` = open, timestamp = resolved.                                            |
| `created_at`             | Row creation time.                                                              |

**Business rules**

- Exactly one of `user_id` or `reporter_email` must be set — never both, never neither. Enforced at the DB layer (see CHECK constraint below).
- Citizens do not have accounts. Their email is captured on the report and stays there.
- **Backfill on signup:** when a new user registers, all reports where `reporter_email` matches the new user's email are updated to point at the new `user_id` (and `reporter_email` cleared). Done via app code or a trigger on `auth.users` insert. See [Open questions](#open-questions).
- `photo_url` is required for fauna/flora report categories, enforced in the application layer once the enum is finalized.
- Reports never expire. `resolved_at` marks the moderation outcome; the row itself is kept.

**CHECK constraint (SQL migration)**

Enforces "exactly one reporter identifier":

```sql
alter table reports
  add constraint reports_reporter_present
  check ((user_id is null) <> (reporter_email is null));
```

### `patrols`

A single Strava-style patrol session. A patroller presses "start", walks a route, presses "end". GPS points captured along the way are stored in `patrol_points`.

**Column descriptions**

| Column       | Description                                                                        |
| ------------ | ---------------------------------------------------------------------------------- |
| `id`         | Internal patrol id                                                                 |
| `user_id`    | The patroller. Always an authenticated user.                                       |
| `started_at` | When the patroller pressed start (client-recorded). Defaults to `now()` at insert. |
| `ended_at`   | `null` = patrol currently active, timestamp = completed.                           |
| `created_at` | Row insertion time (may differ from `started_at` for offline syncs).               |

**Business rules**

- Only volunteers, pros, and admins can create patrols. Citizens cannot.
- A user may have at most one active patrol (`ended_at is null`) at a time. Enforced at the application layer.
- **Live visibility:** patrols with `ended_at is null` appear as active to other users of the app. Polled by the client.
- **2-month visibility window:** by default, the map only queries patrols where `started_at >= now() - interval '2 months'`. This is a query-level filter, not a data-retention rule — older patrols are kept in the DB but not shown on the default map view.
- `started_at` is client-recorded and may drift slightly from server time. Not treated as authoritative for security.

**Indexes**

- `(user_id, started_at desc)` — patrol history per user, most-recent-first
- `started_at` — time-window queries for the default map view
- `ended_at` — fast lookup of currently active patrols

### `patrol_points`

An ordered stream of GPS coordinates belonging to a patrol. Rendered as a polyline for completed routes, aggregated into the frequency heatmap.

**Column descriptions**

| Column                   | Description                                   |
| ------------------------ | --------------------------------------------- |
| `id`                     | Internal point id                             |
| `patrol_id`              | The patrol this point belongs to.             |
| `latitude` / `longitude` | GPS coordinates.                              |
| `recorded_at`            | Client-recorded timestamp for this GPS point. |

**Business rules**

- Points are recorded by the mobile app at a fixed interval (interval TBD with product).
- Ordering within a patrol is by `recorded_at`, not `id`.
- Points are deleted on cascade if the parent patrol is deleted.
- No `created_at` — for high-volume rows the row's timestamp is `recorded_at`.

**Indexes**

- `(patrol_id, recorded_at)` — every route render orders points by this. Critical for performance since this table will grow the fastest.

**Cascade delete (SQL migration)**

```sql
alter table patrol_points
  add constraint patrol_points_patrol_id_fkey
  foreign key (patrol_id) references patrols(id) on delete cascade;
```
