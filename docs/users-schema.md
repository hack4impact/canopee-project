# Canopée Database Schema

Business rules, conventions, and open questions for the Canopée database.

**Sources of truth:**
- Column structure, types, and constraints → [`users-schema.dbml`](../users-schema.dbml)
- Business rules and conventions → this file
- SQL constraints not expressible in DBML → migrations (once Sprint 1 begins)

Visual: [dbdiagram.io view](https://dbdiagram.io/d/6a63e460c3a90dd98db11283)

## Stack

- **Database:** PostgreSQL (via Supabase)
- **Auth:** Supabase Auth handles passwords, sessions, and password resets. Auth users live in the `auth` schema; application user profiles live in `public`.
- **Schema design:** DBML in [dbdiagram.io](https://dbdiagram.io/)

## Conventions

Apply to every table unless a specific table's doc calls out an exception.

- **IDs** are `uuid`, generated by the database.
- **Timestamps** are `timestamptz`.
- **`created_at`** on every table, defaulting to `now()`. Add `updated_at` when a row is mutable.
- **Enum values** are lowercase snake_case.
- **Foreign keys** are named `<table_singular>_id` (e.g. `user_id`, `report_id`).
- **Citizens are not users.** Public reporters interact with the app without accounts; their email is captured on the report itself.

### Where logic lives

- **Structural integrity** (types, NOT NULL, UNIQUE, FK, PK) → database
- **Business rules** (workflow, defaults, product decisions) → application code
- **Security-critical rules** (auth, permissions, data access) → both database (Supabase RLS) and application code

## Enums

### `user_role`
Permission level. Assigned at signup (defaults to `volunteer`) or manually by an admin.

| Value | Meaning |
|---|---|
| `volunteer` | Default role for public signups |
| `pro` | Professional user, assigned manually by an admin |
| `admin` | Full permissions, assigned manually by another admin |

### `user_status`
Approval state for the account.

| Value | Meaning |
|---|---|
| `pending` | Awaiting admin review (default for public signups) |
| `approved` | Active account |
| `rejected` | Denied by an admin |

## Tables

### `users`

Application user profile. One row per non-citizen user. Linked one-to-one with a Supabase Auth user via `auth_user_id`.

For column definitions, types, and constraints see [`schema.dbml`](../schema.dbml).

**Column descriptions**

| Column | Description |
|---|---|
| `id` | Internal user id |
| `auth_user_id` | Links this profile to the Supabase Auth user. Cascade delete. |
| `email` | Contact email. Duplicated from `auth.users.email` for convenience. |
| `role` | Permission level. See `user_role` enum. |
| `status` | Approval state. See `user_status` enum. |
| `created_at` | Row creation time |

**Business rules**

- Public signups create `role = 'volunteer'`, `status = 'pending'`.
- Pros and admins are created manually by an existing admin. They are never created through the public signup form.
- Admins are always `approved`. Enforced at the application layer per the convention above.
- Passwords are not stored here — Supabase Auth handles password hashing and validation.
- Permissions derive entirely from `role`. There are no per-user permission flags.

**FK to `auth.users`**

Not visualized in dbdiagram because it targets a schema (`auth`) that dbdiagram doesn't know about. The constraint is added in the SQL migration:

```sql
alter table public.users
  add constraint users_auth_user_id_fkey
  foreign key (auth_user_id) references auth.users(id) on delete cascade;
```
